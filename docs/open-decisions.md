## BUG-04：辅助图组开关的语义（待定）

**状态**：待定，暂不修改行为。
**影响**：`WorkflowGraphs.analyze` / `WorkflowDecision` / 两端节点图选择 UI。

### 现象

节点图列表里，一个节点图的选中/取消看起来像「开关」，但对普通组来说是空操作：

- 勾选：把组内**在文件里本来就是旁路/静音**的节点临时恢复执行（`forcedNormalNodeIds`）；
- 取消：撤掉这个临时启用，回到文件里保存的状态。

因此当组内节点本来就正常时，勾和取消都没有可见变化，用户会以为开关坏了。
（这个语义对辅助图组是有意的：参考图组 `image-2..8` 需要在选中时才把 LoadImage 拉起来。）

### 两个候选方向

**A. 真·整组开关**

取消时把组内**正常**的节点也旁路，让「关组」真的有执行上的效果。

- 需要新增 `forcedBypassNodeIds`（会话级强制旁路），并让它贯穿：
  `UiWorkflow.withEffectiveModes` → `PromptBuilder.build` → `WorkflowDecision` →
  两端节点图选择 UI；
- 优先级要定清楚：`forcedBypass` 与用户单节点 `enabledNodeIds` 谁优先？
  建议单节点显式开关优先（用户点过就该听用户的）；
- 副作用：关掉一个含输出节点的组会让工作流不可提交，需要确认框；
- 测试：整组关 → 该组节点不进 prompt；整组开 → 原本旁路的节点进 prompt。

**B. 保持现状，只改文案**

接受「组开关只负责把组内被旁路的节点拉回来」，把 UI 文案改成
「启用组内被关闭的节点」，不再用开关样式/措辞。

- 改动只在两端 UI 文案与提示，不碰共享层；
- 代价：用户仍然不能一键关掉整组，节点多的工作流要逐个关。

### 决定前需要确认的一件事

这两种语义在「输出图」和「辅助图组」上是否要一致？输出图取消选中本来就不提交，
和 A 的效果接近；辅助图组取消选中则只是回到文件状态。如果两处要一致，倾向 A。
